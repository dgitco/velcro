# velcro for agents

velcro is a macOS (13+) menu bar app and `velcro` command. It keeps SMB and NFS shares mounted, imports recordings from a USB voice recorder into any folder, and sends files to an inbox folder. Everything is configured with `velcro` commands or the app's Settings; users never need to edit code.

## If the user wants to use velcro

Do these in order. Ask before adding or changing anything, and change things only with `velcro` commands.

1. **Install.** `curl -fsSL https://velcro.dgit.co/install | sh` installs the menu bar app and the command. For the command only (no app): `curl -fsSL https://velcro.dgit.co/install | sh -s -- --cli-only`. The command lands in `~/.local/bin/velcro`; use that path if it isn't on `PATH` yet. From a clone of this repository, `./velcro install` does the command-only setup.
2. **Shares (only if they have a NAS or file server; skip otherwise, `velcro status` then just says there are none).** List what's mounted now with `mount -t smbfs` and `mount -t nfs`, show the user, and add the ones they pick: `velcro add smb://user@host/share` (spaces as `%20`). If they also reach the server another way, such as a Tailscale name, append it as a fallback host: `velcro add smb://me@192.168.1.10/home nas.tail1234.ts.net`. If macOS asks for a password, tell them to tick "Remember this password in my keychain".
3. **Voice recorder (optional, no NAS needed).** With the recorder plugged in: `velcro recorder add /Volumes/<its name>` (without the path it only works when that is the only external drive mounted). **Set these in this order, because importing (and deleting from the recorder) starts as soon as `import.dest` is set:** (a) look inside the recorder; if recordings live in one folder (often `RECORD`), `velcro set import.folder <that folder>` so nothing else on it (music, settings files) is touched; (b) ask whether to delete recordings from the recorder once copied and verified (the default); if not, `velcro set import.delete no`; (c) ask where recordings should go (a folder on the Mac such as `~/Recordings`, iCloud Drive, an external drive, or a share) and run `velcro set import.dest <folder>` last. A folder outside `/Volumes` must have an existing parent (velcro creates only the last folder). With deleting off, files already imported are skipped by the manifest and the recorder is ejected only when something new was copied. For a share, use the path it's actually mounted at: if macOS mounted it as `/Volumes/home-1`, a folder under `/Volumes/home` never counts as attached and recordings wait on the Mac. `velcro import` runs it now.
4. **Send to an inbox (optional).** `velcro set send.inbox <folder>`: a folder on a share, or one Dropbox or Syncthing keeps in sync. The folder's parent must exist: for Dropbox, check where it lives (newer installs use `~/Library/CloudStorage/Dropbox`, older ones `~/Dropbox`). If another machine (for example a server they use over SSH) sees that folder at a different path, `velcro set map "<path on this Mac> -> <path there>"`; the left side may start with `~/`, and several rules go in one command (`velcro set map "<a> -> <b>" "<c> -> <d>"`) or one at a time with `velcro set --add map …`. Then `velcro send <file>` (or the app's Send to Inbox menu) saves the file there and copies its path; nothing is sent automatically. Files velcro sent are deleted after `send.keep` days (14); other files in the folder are never touched.
5. **Mac mic (optional, needs the app).** Only if they use a Linux machine over SSH and want voice input there (Claude Code's `/voice`, for one). Check that `ssh <host> true` works without a password prompt, then `velcro mic on <host>`: it installs `velcro-mic-host` in `~/.local/bin` there, checks PipeWire, and starts lending the microphone. Tell them macOS will ask once to let velcro use the microphone, and that it opens only while something on that machine is recording. If the check says PipeWire is missing, stop and tell them; don't install packages on their server unasked. `velcro mic off` stops it; `velcro mic remove` deletes the helper.
6. **Transcribe (optional, no app or NAS needed).** Only if they want audio files (a Slack voice memo, a recording) turned into text. They must be signed in on this machine with their own account to Claude Code, or to Codex with ChatGPT (`codex login`; an API key is never used); never use or copy anyone else's login, and tell them this uses Claude Code's or ChatGPT's own speech-to-text, not a public API, and that ChatGPT keeps the audio for 30 days. velcro tries Claude first, then Codex, each only if signed in; if they want only one or the other order, `velcro set transcribe.engine <claude|codex> [the other]`. `velcro set transcribe.lang <code>` if they don't speak English (`ko`, `ja` …), then `velcro transcribe <file>`. Only if they ask for a backup engine: `velcro set transcribe.fallback "<command that takes the file last and prints text>"`.
7. **Process recordings (optional, usually on a server that has the recordings share mounted).** Only if they want every imported recording transcribed and handed on automatically. Ask which engine; there is no default. Suggest a local command such as whisper.cpp for meetings; `claude` and `codex` use their login (step 6) and are meant for memos, so set one only if they ask, then `velcro set recordings.dir <folder>`, `velcro set recordings.engine <claude, codex or command>`, optionally `recordings.tidy` / `recordings.deliver` / `recordings.alert` commands they already have, and `recordings.since <today>` so old recordings are left alone. Check with `velcro recordings`, then `velcro recordings run`. Suggest a timer (systemd or cron, every few minutes) rather than installing one.
8. **Finish** with `velcro status`, `velcro settings`, and `velcro mic`, and tell the user what's set up.

`velcro help` lists every command and setting. Logs: `velcro logs`. Undo: `velcro rm <share>`, `velcro recorder rm <name>`, `velcro set <key>` (back to default), `velcro uninstall`.

## If you're working on this code

- `velcro` (zsh) does all the work; `app/` (SwiftUI, xcodegen) runs it for the menu bar. The exception is Mac Mic: `app/Sources/Mic.swift` holds the SSH session and the microphone itself, and `velcro-mic-host` (Python, runs on the Linux side) adds the PipeWire microphone and prints `start`/`stop`. Test the helper on Linux without a Mac by feeding it PCM and recording with `arecord`. PipeWire's pipe source buffers 8192 frames whatever the rate, which is why the helper runs the FIFO at 96 kHz. `app/Tools/velcro-sha` is a small command that hashes a file with the cache off (F_NOCACHE); the app puts it in `Contents/MacOS` and the installer puts it next to a command-only install. Without it, reading back a copy just written to an SMB share returns cached data. The version is `VERSION=` in `velcro`.
- `velcro transcribe` hands the talking to `velcro-transcribe` (Python, stdlib only, Mac or Linux), which holds the voice_stream WebSocket (Claude Code's own speech-to-text, found in its bundle by `voice_stream`) and, for `codex`, posts to ChatGPT's `backend-api/transcribe` with the ChatGPT login in `~/.codex/auth.json` (5-minute pieces: ChatGPT drops text past about 10 minutes and fails at 25). It reads the user's Claude Code and Codex logins and must never renew, print, write or share them, and never uses an OpenAI API key. Tests: `python3 -m unittest discover -s tests`.
- `velcro recordings` hands the settings to `velcro-recordings` (Python, stdlib only), which reads the import manifest, runs the engine and the hook commands, and keeps failure counts and a lock in `~/.local/state/velcro` (Linux) or Application Support (Mac). Tests: `tests/test_recordings.py`, with fake engines and hooks.
- Build: `scripts/build-app`. Site: `scripts/deploy-site --stage` prepares `site/public`; without `--stage` it also deploys.
- Test with a throwaway `HOME` (`env -u XDG_CONFIG_HOME HOME=/tmp/x zsh ./velcro …`) and a disk image as a fake recorder (`hdiutil create -fs MS-DOS …`). `velcro install` and `uninstall` call the real `launchctl` and remove the real SwiftBar plugin even with a fake `HOME`, so put stub `launchctl`, `defaults`, `open`, and `osascript` first on `PATH` when testing them.
- With `pipe_fail` on, don't `return` from inside `cmd | while …`; loop over an array instead.
- Keep personal hosts, user names, and paths out of the repository; examples use `nas.local`, `/Volumes/home`, `/mnt/nas/me`.

### Development rules (shared, 2026-10-15)

- **Squash merge only.** The PR title becomes the commit title on main, the PR body its message.
- **Update a branch with `git rebase origin/main`, then `git push --force-with-lease`.** Never merge main into a branch.
- **main is protected.** No direct pushes, force pushes or deletion, and no admin bypass merges. Every change goes through a PR.
- **PR body: Background · Change · Screens (before/after) · Risk** ([template](.github/pull_request_template.md)). If the UI changes, attach before/after images (video for motion). **A UI change without images is not merged.** No UI change: "N/A — why".
- Upload images and videos with `shot-upload <file>` (public R2 bucket `pr-shots`; prints the URL and markdown). Where it isn't installed, drag the file into the PR editor. Links are public: use fake data or blur anything personal.
- **Dependent changes go in a stack with `gh stack`** (`gh stack init` → `gh stack add` → `gh stack submit`). One thing per layer; split when the non-test diff passes about 400 lines.
- **Tests cover API contracts, permission boundaries, money/date calculations and migrations only.** No tests that pin CSS classes, copy, layout, or jsdom viewports. Tests that need a database: tenant isolation and money only.
- **Merge condition: a review pass by an agent other than the one that wrote the PR, plus evidence.** The reviewer (e.g. a subagent that doesn't know the writing conversation) checks correctness, requirements and evidence only; trivial findings are not acted on. No waiting for human approval.
